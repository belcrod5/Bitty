# オーケストレーションチャットの継続学習設計

状態: 2026-10-21、段階1〜3の実装に対応。本文は2026-10-20の設計判断と導入時の検証条件を記録する。学習・評価用モデル設定、採否と反映撤回、専用スキルの公開と可視化、適合度の訂正、利用量・料金ログを実装した。操作と実測の範囲は[実装・確認手順](ORCHESTRATOR-LEARNING-OBSERVATION.md)を参照。実利用での長期改善率は未検証であり、スキルの自動公開は無効のままとする。

## 1. 目的と結論

会話を重ねるほど、ユーザーが同じ説明や訂正を繰り返さずに済むようにする。指示の傾向から記憶とスキルを育て、次の行動や複数タスクのまとめ方を提案する。「成長」は記憶量ではなく、再指示の減少と提案の有用性で測る。

各ターンで行うのは確定した会話の差分記録までとする。独立した非同期LLMは差分をまとめて分析し、根拠付きの学習候補を生成する。検証した候補だけを応答へ反映し、繰り返し使われる手順だけをスキルへ昇格させる。推奨案では、固定システムプロンプト全体の自己書き換えではなく、学習する応答方針を別の低優先コンテキストとして自動生成・調整する。以下のスコープ・閾値・昇格方法は実装の承認済み決定ではなく、設計上の提案である。

根本的に足りないのは会話の保存先ではなく、**確定した会話 → 学習候補 → 検証・反映 → 利用結果による修正**の契約である。この契約をRunner側に設け、チャットUIや個別タスクごとの特例を増やさない。

## 2. 確認した現状

以下は設計開始時に確認した既存境界である。後述の学習機能を、これらの境界と既存の承認経路に接続した。

| 境界 | 現在の役割と制約 |
| --- | --- |
| [voice-context-service.mjs](../private_runner/src/voice-context-service.mjs) の `append` / `runTurn` | `completed`イベントを同期書き込みした後、ユーザー発話と応答のpairを保存する。表示ストリーム終了や通知配送とは別の確定境界がある。 |
| 同ファイルの `startSummary` | 未要約pairから直近10件を除いた差分と既存topicsを非同期LLMへ渡す。現在は応答用model/effortが既定であり、`topicModel`は話題切替判定用である。 |
| [voice-memory-store.mjs](../private_runner/src/voice-memory-store.mjs) | 出典付きtopics、世代切替、cursor、rawを管理する。rawは30pair保持・最大40pair。要約が進まないと会話受付に影響し得る。 |
| [voice-orchestrator-service.mjs](../private_runner/src/voice-orchestrator-service.mjs) | 複数チャットでworkspaceとmemory storeを共有。`pairExclusive`で採番・追記を直列化し、main側に要約を集約する。 |
| `responseInstructions` / `modelTurn` | チャット別`systemInstruction`と固定の実行規則を合成する。親セッション継続時は過去pairを再注入しない。記憶や過去会話は指示ではなく文脈として扱う。 |
| `clearMemory` / `clearMessages` / `remove` | 記憶クリア、メッセージクリア、チャット削除は異なる操作。記憶クリア後も保持rawから再要約し得る。チャット削除だけでは共有記憶は消えない。 |

現行の要約は事実の圧縮を担う。反復回数、適用条件、誤学習の取消、スキルへの昇格、採用した提案の結果を扱う契約はない。要約へ学習を単純に混ぜると、学習の遅延や失敗が既存のraw容量・会話受付へ波及する。

## 3. ユーザーに現れる変化

| 会話から得る根拠 | 期待する変化 | 誤った一般化を防ぐ条件 |
| --- | --- | --- |
| 複数の依頼で「報告は短く」と訂正 | 同種の報告を短くする | 「今回は短く」はその依頼だけ。詳しい説明を求められたら現在の指示を優先する。 |
| 毎回「指定文書を読み、worktreeで調査」 | 同種の依頼で手順候補を提示し、安定すればスキル化 | リポジトリ固有の手順を全チャットへ無条件に広げない。 |
| 同じ分類・整形を複数対象へ依頼 | 「残りの対象も、この条件でまとめて処理しますか」と提案 | 対象・件数・除外条件・副作用を示す。似ているだけの別作業は束ねない。 |
| 先回り提案を繰り返し断る | 同じ提案を控える | 拒否はその提案の範囲に結び付け、ユーザー全体の性格として記録しない。 |

先回りは通常の応答ターンで行う。ユーザー不在の自動実行、通知の連発、過去の同意の使い回しは導入しない。未確定の推測を毎回質問に変えることも避け、根拠が弱ければ提案しない。

## 4. 最小構成と責務

```text
既存のcompleted確定・復旧経路
        ↓ 差分と出典を記録（LLMを待たない）
共有workspaceの学習状態
        ↓ 件数・時間・予算で起動
独立した非同期分析（ツール使用不可）
        ↓ 構造・出典・矛盾・スコープを検証
候補 / 有効項目 / 廃止項目
        ↓ 応答開始時に適用候補を取得
既存の応答コンテキスト → 提案 → 現在の許可に基づく実行
        ↑ 次の確定会話で訂正・採用・拒否を観測
```

- `voice-context-service`は、既存の会話確定・復旧と応答への受け渡しを担当する。
- `voice-orchestrator-service`は、共有学習サービスの所有とチャットID・ライフサイクルの接続を担当する。通知用`onCompleted`だけを正本にしない。
- 新設するなら`orchestrator-learning-service.mjs`一つに、学習項目の遷移、入力選別、取得、永続化をまとめる。独立した責務の抽出であり、汎用ジョブ基盤や各処理を転送するだけの層は作らない。
- 既存のread-onlyな`modelTurn`経路を利用する。学習側へ分析実行関数を渡す最小接続を先に検証する。LLMクライアントや承認処理を複製しない。共通化が必要でも実際の要約・学習の2用途に必要な部分に限る。
- `voice-memory-store`の事実要約とcursorは維持し、学習状態と失敗を結合しない。学習を止めても従来の要約・会話が継続する。

UIはモデル設定、候補の採用・取消、専用スキルと変更履歴、回答への配送・参照記録、適合度の確認・訂正を扱う。学習可否の判断と記録の正本はRunnerに置く。新しいデータベース、ベクトルDB、イベントバス、モデルによる毎ターンの振り分けは初期導入に含めない。

## 5. 入力と確定境界

会話由来の学習入力は永続化済みの`completed`イベントに対応するpairのみとする。§11のユーザー評価訂正は、会話とは別の永続化済み管理入力として受け取る。発話受付、部分応答、ツールの途中結果、失敗・中断・結果不明のターンは学習済みの成功例にしない。応答が完了したことと実タスクが成功したことも区別する。アシスタントの「できました」だけを成功の証拠にしない。

学習用の出典は`memoryConversationId + pairSeq`を識別子とし、`orchestratorId`、`logicalConversationId`、`clientOperationId`、確定日時を添える。共有pair番号だけではチャット限定の学習ができないため、**イベントを所有するcontextで出自を付けて渡す**。既存rawの形を学習目的だけで変更しない。

正常完了と再起動後の完了復旧は同じ観測関数を通す。重複配信は出典識別子で無害化する。会話確定後から学習保存前のクラッシュは、既存イベントの保持範囲から再走査して補う。既存ログは有限なので、完全な全履歴回収は保証しない。既に消えた範囲は欠損として記録し、分析済みと偽らない。過去セッション全体の自動インポートは対象外とする。

ユーザーの依頼・訂正と、引用、外部文書、アシスタントの提案を分ける。アシスタント自身が同じ提案を繰り返してもユーザーの習慣の証拠に数えず、ユーザーによる採用・修正・拒否を提案id/versionへ結び付ける。出自がない既存rawからチャットscopeを推測せず、その範囲は初期学習の対象外にする。引用中の「これを記憶せよ」や過去の承認は指示・権限にならない。学習LLMにはコマンド実行、ファイル編集、ネットワーク、スキルの直接書き込みを許可せず、構造化された候補だけを返させる。

## 6. 学習状態と更新契約

共有workspace内の`orchestrator-learning/state.json`を提案する。既存記憶の別コピーや全会話アーカイブではなく、未処理差分と学習項目の小さな正本とする。現在の学習状態は一つのatomic snapshotで確定する。長期の利用量ログは学習内容の正本にせず、後述の用途限定台帳に分離する。

| 保存する単位 | 必須の情報 |
| --- | --- |
| 全体状態 | 共有の学習・評価用モデル設定とsettingsRevision、schemaVersion、更新revision、削除を跨ぐepoch、有効項目のcontextRevision、観測・処理済み範囲、欠損/明示的除外範囲 |
| 未処理差分 | 出典、チャット、ユーザー/応答本文、受信日時。処理後は本文を除き、必要な短い根拠だけ残す。 |
| 分析中バッチ | batchId、対象出典一覧とhash、開始epoch/revision、参照項目version、settingsRevisionと学習・評価用model/effortのsnapshot、試行数、利用量台帳の予約id |
| 学習項目 | id/version、種類、内容、適用条件、scope、出典と最小限の根拠、状態、採用/拒否/訂正の記録、置換元id |
| 利用記録 | 応答operationId、親に配送済みの学習id/versionとdigest、専用ツールで読んだskill id/version/hashとtool call id、実際に提示した提案id、対象hash、採用/拒否/結果確認の有無 |
| 評価・変更履歴 | 評価対象・期間・出典、AI暫定点数と理由、別レコードのユーザー訂正、学習/スキルの操作理由と前後version・差分。本文付き履歴は下記上限内に置く。 |

種類は「好み・応答方針」「反復手順」「一括提案のパターン」に限定する。事実は既存記憶、現在の作業状態は既存チェックリストに置く。同じ事実・To Doを学習項目にも複製しない。

状態は`candidate → active → retired`を基本とし、却下候補は`rejected`とする。LLMの自己申告スコアだけで昇格させない。出典の存在、明示指示か推測か、独立した依頼での反復、矛盾、範囲、利用結果を使う。同一依頼内の言い直し・再送は独立した反復として数えない。

保存は単一writerで直列化し、temporary file・fsync・renameを使う。分析結果と処理済み範囲の更新を同じsnapshotで確定する。LLMが候補なしと判定した有効なバッチも処理済みにする。LLM失敗・不正JSON・出典不正では進めない。

分析中の新pair追記だけなら、取得時点の出典hashと参照項目versionが同じであることを確認して現在状態に結果を適用する。訂正・取消・スコープ変更・削除と競合した結果は棄却する。追加pairは次バッチへ回す。単に古いsnapshot全体で上書きしない。

## 7. 費用を抑える起動条件

毎ターンLLMを呼ぶのではなく、コードによる件数・時間・容量・予算の判定で起動する。キーワード一致を唯一の学習条件にはしない。キーワードがなくても一定量の差分が集まれば分析される。

以下の数値は**提案初期値であり未測定**。ユーザー設定を多数増やす前に、実測で調整する内部定数とする。

| 項目 | 提案初期値 |
| --- | --- |
| 起動 | 未処理8pair、または最古の未処理pairが10分経過。実行中応答があれば待つ。 |
| 呼出間隔・並行数 | 最短5分、共有workspaceごとに同時1件。チャットごとにLLMを増やさない。 |
| 1回の入力 | 最大16pair、本文と参照項目を合わせて24,000 UTF-8 bytes。巨大な1pairは境界を明示して部分入力とし、その出典から自動昇格しない。 |
| 出力 | 最大4,000 tokens。利用ランタイムで強制できるか導入前に確認する。 |
| 日次予算 | 最大12呼出・入力出力合計100,000 tokensの両方を上限とする。評価・失敗・再試行も含む。 |
| 未処理保持 | 最大128pair、合計1 MiB、7日。上限時は古い未処理本文を落とし、除外範囲と理由を残す。 |
| 学習項目 | active最大50件、candidate最大100件・30日。rejected/retiredは本文付き最大100件・90日とし、期限後は再学習除外に必要な識別子だけ残す。 |
| 根拠・利用記録 | 項目ごとの根拠抜粋は最大3件・計2,000 bytes。利用記録は最大500件・30日。採否は項目id/versionごとの集計と最新の対象hashへ畳み込む。 |
| 評価・変更履歴 | 各100件・90日、各レコード最大8,000 bytes。未反映のユーザー訂正は期限で落とさず、反映先versionに紐付けてから整理する。 |
| 学習状態全体 | state.jsonは最大4 MiB。評価・変更履歴を含む。本文を落としても除外識別子は保持し、圧縮不能なら学習の取込・昇格を保留する。 |
| 応答への取得 | 最大5件、計4,000 UTF-8 bytes。関連がなければ0件。 |

観測・処理・欠損・除外は連続する範囲を統合して保持する。却下や忘却を防ぐ識別子を単なる期限切れで捨てない。再注入除外が必要な利用pairは、通常の利用記録の期限切れ前に除外範囲へ移す。記録容量の限界では保護情報を捨てず学習を止め、理由を表示する。候補作成の保留で要約・会話は止めない。

新規差分と関連項目だけを分析に渡す。候補の適用条件・チャット・対象種別で既存項目を絞り、毎回全topicsや全スキルを読み直さない。件数増加に備える検索基盤は今は作らない。

### 学習・評価用モデルの設定

[既存のモデル設定UI](../expo/src/features/app/components/VoiceOrchestratorManager.tsx)と同じモデル一覧・対応effortの選択方法で、「学習・評価用モデル/エフォート」の一組を追加する。最初は学習と評価を同じモデルで処理し、別々の設定は増やさない。応答、話題判定、To Do表示の設定とは独立させる。共有workspace全体で一つの設定を学習サービスが所有し、UIにも「全オーケストレーター共通」と表示する。選択中チャットやmainチャットの応答設定を暗黙の所有者にしない。

設定保存はsettingsRevisionを指定して競合を検出する。バッチ開始時にこの一組の設定を固定し、変更は次バッチから適用する。同じバッチの再試行や追加検証は旧snapshotを使い、設定変更で途中の処理結果を混ぜない。利用不能なモデル/effortは検証エラーまたは保留とし、無断で別モデルへ切り替えない。設定変更後の明示再試行は新バッチとして記録するが、元入力の試行回数・消費予算は引き継ぐ。

少数の固定評価例で品質を確認し、高品質モデルの呼出頻度を下げる方針を基本とする。一つの差分分析呼出で学習候補と変化があった対象の暫定評価を返し、変化のない対象は再評価しない。毎ターンの安価モデル判定や通常評価の別呼出は導入しない。重要な統合・昇格検証に限り追加呼出を行い、同じ設定と予算枠を使う。

予約時に入力見積りと最大出力を予算から差し引き、完了時のusageで精算する。不明なusageは予約分を消費扱いにする。予約・精算の正本は次節の利用量台帳に置き、再起動後もUTC日付境界の日次集計へ一度だけ算入する。利用環境が出力上限を強制できなければ、厳密なtoken上限とは呼ばず、呼出数制限と保守的予約で制御する。価格は契約・モデルで異なるため、本書では金額や削減率を断言しない。

予算超過時は学習だけ延期する。非同期にしても無料にはならず、モデルの同時利用資源も消費する。通常応答の開始時には学習の新規起動を止め、実行中分析の中断要否と応答遅延を計測する。

### 後から分析できる利用量・料金ログ

対象は今回追加する学習、適合度評価、スキル作成/編集/統合/廃止の分析と検証に限る。既存の応答・要約・話題判定などを一斉に改修する共通課金基盤は作らない。現行`modelTurn`は主にoutputTokensを返し失敗時はthrowするため、そのままでは全試行の費用を記録できない。今回の呼出経路に、失敗時を含むusage取得と終了記録の境界を設ける必要がある。input/cache等の取得契約は導入前に確認する。

`orchestrator-learning/usage/`に用途限定の台帳を置く。呼出前の予約と終了時の更新を同じcallIdのレコードに保存する。リトライはattemptごとの別callIdとし、同一batchIdに結び付ける。候補と評価を同時に返した一呼出を用途別に二重計上せず、重要な統合検証等の追加呼出だけ別記録にする。

| 呼出レコード | 保存内容 |
| --- | --- |
| 識別・結果 | callId、batchId、attempt、用途（通常の学習・評価は一つの複合用途）、開始/終了UTC、完了/失敗/中断/結果不明、理由コード。会話本文、プロンプト、応答、API鍵は保存しない。 |
| 設定と実行 | settingsRevision、要求model/effort、provider/runtime、実際に報告されたmodel/effort、取得できたrequest/turn id。実際値が不明なら要求値で埋めず不明とする。 |
| 利用量 | input/output、cached input、reasoning等の内訳、取得元とusage schema、実測/部分取得/欠測、予約量・見積量。総量と内訳の包含関係を保持する。 |
| 料金計算 | 単価表version、出典、通貨、単価の単位と適用開始日時、適用した契約種別、計算式version、算定額/算定不能。適用した区分別の数値単価を保存するか、その不変snapshotを参照し、外部価格表の更新後も算定を再現できるようにする。価格をコードへ固定せず、実呼出時点の根拠を保存する。 |

cached inputがinputの内数、reasoningがoutputの内数なら、それぞれを総token数へ再加算しない。料金はそのproviderの単価区分に分解して算定し、包含関係や区分が確認できなければ算定不能にする。usageイベントのlastとtotalは両方を加算しない。累積値なら当該thread/turnの開始基準から呼出範囲の差分を採り、過去ターンや再通知を算入しない。基準が取得できず呼出への帰属が確定しない値は部分取得/欠測として残す。失敗や中断でも報告されたusageは残す。欠測はnullと欠測件数で示し、0 tokens/0円と表示しない。予約量を実測量へ転記せず、予算制御と利用分析を分ける。

金額はusage実測がある場合も料金表による算定であり、請求書の実額とは区別する。定額契約、無料枠、割引、税、為替等により一致しない。契約対応の単価が不明ならtoken数のみを表示する。異なる通貨をそのまま合算せず、価格改定後も過去の算定を上書きしない。新単価での再計算は別の比較表示とする。

台帳は単一writer・atomic更新で扱い、予約を永続化してから呼び出す。クラッシュ後に結果を照合できない呼出は「結果不明」のまま予約分を予算消費扱いにする。後からusageを回収できた場合だけ同じcallIdを精算し、再試行を旧呼出と同一視しない。予約保存に失敗したら裏側AIを起動せず、記録更新失敗時は新規の裏側呼出を停止して復旧を待つ。通常会話は止めない。

保存の提案初期値は、呼出明細90日・最大10,000件かつ20 MiB、日次集約400日・最大4 MiBとする。学習のstate.json上限4 MiBとは別枠で、全体を無制限に増やさない。日次集約はUTC日・用途・設定revision・実モデル/effort・usage状態・単価表/通貨を軸にし、呼出/失敗/欠測件数、実測token、予約扱い量、算定可能額と算定不能件数を保持する。期間を指定した分析には保持開始日、欠落、集約粒度を表示し、比較可能な目標/期間の評価結果と組み合わせて品質と消費量を検討する。

明細を落とす前に、対象callId集合のhashと集約済み境界を含む集約を永続化し、その後に明細を削除する。集約済み明細を再集計しない。保持明細に対応する遅着usageは旧寄与を置換する訂正として一度だけ反映する。個別対応を削除した後の遅着値は未照合とし、推測で集約へ加えない。件数/容量制限で期限より早く明細を整理した場合も、その範囲を表示する。集約しきれない上限・欠損時は新規呼出を保留し、集計を完全と偽らない。

費用台帳から学習内容を復元しない。忘却時は学習項目・スキル・評価・出典との対応を切り、本文を含まないモデル別の利用量と料金算定は保持する。台帳削除を明示された場合は分析履歴を削除し、当日予算をリセットしないための匿名の消費合計・未精算予約だけ日付境界まで残すことを表示する。

## 8. 反映・優先順位・スコープ

取得契約は`現在の入力 + orchestratorId + 実際に確認できた対象情報`を受け取り、`contextRevision + 有効な項目id/version + 適用条件 + 短い内容 + 出典`を返す形とする。対象情報がないのにリポジトリや作業種別を推測して適用しない。取得はコードで範囲・状態・容量を絞り、意味上の最終適合は通常応答LLMが現在の依頼と照合する。

優先順位は、固定の安全・承認・実行契約を最上位とし、その範囲内で現在の明示依頼、ユーザーが設定したチャット方針、採用済みの学習方針、推測候補の順とする。現在の依頼とユーザー設定が明確に衝突するときは学習で勝手に解決しない。推測候補は自動行動の根拠にしない。

`systemInstruction`の自動生成・全面置換は行わず、学習可能なのは長さ、表現、依頼の進め方、提案タイミングなどの限定した方針とする。固定プロンプトは「根拠付き項目をどう利用するか」を定義し、学習内容は分離した構造化contextとして渡す。ユーザーが手動で書いた設定を編集する場合は、別途差分を提示してその変更への許可を得る。

scopeはまず`orchestratorId`限定とする。ユーザーが全チャット共通と明示するか、複数チャットで同じ傾向が確認され採用された場合にだけ共有へ昇格させる。「このチャットだけ」は共有に昇格させない。scopeが共有でも、適用条件（対象リポジトリなど）は残す。共有workspaceは別ユーザーへ学習を広げる根拠にはならない。

### 継続中の親セッションへの反映

保存しただけでは応答が変わったことにならない。現行は継続親へ過去pairを再注入しないため、新しいcontextの配送と撤回を実装前に確認する。

1. 初期導入では、応答開始時に学習snapshotを固定する。有効項目変更時だけ`contextRevision`を進める。取得した項目id/version・適用条件・内容を正規化してdigestを作り、親に適用済みの`contextRevision + selectedDigest`を保持する。
2. revisionまたはselectedDigestが異なる場合は既存の安全な親切替境界を利用し、新しい親へその時点の学習contextを渡す。同じrevisionでも依頼が変わって取得項目が変われば切り替える。0件への変更も旧方針の撤回として扱う。候補生成や未処理pair追加だけでは親を切り替えない。共有変更は各チャットの次ターンで反映する。選別による切替頻度と遅延は段階2で計測する。
3. 子作業が未完了などで安全に切り替えられない場合、通常の追加学習は反映待ちとする。取消・忘却・今回の適用範囲外によって除外される項目を含む親では新ターンを開始せず、安全な切替を待つ。現在進行中の外部操作を学習側から取り消したことにはしない。
4. 親切替時に再注入するrecent pairsにも取消済み方針の発言が残り得る。学習項目の出典または利用記録に対応するpairは、その取消後の自動文脈再注入から除外する。履歴原本は変更しない。識別できない旧文脈を安全に分離できない場合はrecentの再注入をせず、現在の依頼と有効contextから再開する。失効項目の本文を「取消一覧」として再注入しない。
5. 将来、継続親でcontextを置換するAPI契約が実機で確認できた場合だけ、切替コストを減らす。単なる追加メッセージで古い方針が消えるとはみなさない。

応答コンテキストに渡した項目と、実際に提案・使用した項目を区別して記録する。先回り提案の直後に同じユーザー依頼が来ても、同一提案を繰り返さない。提案対象hash、採否、現在の依頼を確認する。

## 9. スキル化と一括処理

最初から全候補を`SKILL.md`にしない。単一の好みは短い学習項目に留め、複数段階の安定した手順と適用条件があるときだけスキル候補にする。

提案する昇格条件は、別の依頼で3回以上確認され、少なくとも1回は手順の結果が確認でき、反例・適用外条件が説明できること。これは未測定の初期基準であり、回数だけで品質を保証しない。明示的な「スキルにして」は候補作成を早めるが、内容検証は省略しない。

生成スキルは目的、発動条件、入力、手順、出力、例外、承認が必要な操作を持つ。個人情報・秘密・具体的な過去の操作権限を埋め込まない。スキルの採用と、それを使った外部操作の許可は別である。学習LLMはMarkdown案を返すだけとし、検証済みartifactの公開はRunnerの管理操作で行う。

管理対象はこの機能が作ったスキルだけとし、id/version/content hashを学習項目に結び付ける。ユーザー管理・既存インストール済みスキルの直接編集・削除はしない。類似する既存スキルがあれば重複生成せず、差分案を提示する。手動編集で管理対象のhashが変わった場合も自動上書きを止める。

統合では複数の発動条件・反例を保持できるか評価し、後継スキルを検証してから旧版を`retired`にする。削除はまず取得対象から外す論理廃止とし、直前版へ戻せる。明示的な忘却は保存版も削除対象になる。学習項目が正本、スキルはそのversionから生成した成果物とし、両者で手順を別々に編集しない。

### オーケストレーター専用スキルと可視化

生成物は共有workspace内の`orchestrator-learning/skills/`へ置き、Codex全体の共有スキルディレクトリとは分離する。scopeは当該オーケストレーターまたは同じworkspace内で明示採用された共有範囲だけにする。専用読取ツールで、呼出元のorchestratorIdと有効versionをRunnerが検証して取得する。任意パスを指定して他scopeを読む契約にはしない。スキル選択・公開版変更も§8の配送digestと失効規則に含め、生成しただけで起動中の親が読んだとはみなさない。

UIでは一覧に名前、候補/有効/廃止/却下、適用範囲、版、更新日時を表示する。詳細には裏側AIによる作成・編集・統合・廃止の理由、出典、前後の差分、採用/却下の決定者を表示する。進行中アクティビティ表示を永続履歴とみなさず、変更確定時の記録を表示する。履歴は§7の件数・期間・state.json容量内に置き、保持外の履歴は表示できないことを明示する。差分や理由を別の正本で編集しない。生成ファイルは正本versionから再生成できる派生成果物とし、現行版と取消用の直前版だけを保持する。全生成物最大4 MiBを提案し、超過時は公開を保留する。

各回答の詳細には「モデルに渡した学習」と「ツールで参照した専用スキル」を区別して表示する。前者は成功した親/ターン配送と適用digest、後者は成功した読取tool callと返却skill id/version/hashを根拠にする。選別しただけの項目は配送済みにせず、LLMの自己申告を参照記録にしない。継続親で以前に読んだスキルは「親に残る参照」として現在ターンの読取と区別し、参照記録が取得不能なら未確認と表示する。配送・読取が回答へ実際に影響したという因果関係は証明しない。

専用ツールの起動中親への登録・更新可視性とUIの詳細は導入前に検証する。段階2で学習項目の回答への配送表示を導入し、専用スキルの公開・一覧・差分履歴・ツール参照表示は段階3に導入する。

一括提案はスキルと同じ反復手順を利用する。現在確認できる対象を列挙し、共通手順、件数、除外、処理順序、失敗時の扱いを一つの提案にまとめる。許可された集合と操作だけを実行する。後から増えた対象、異なる副作用、結果不明の再実行を「一括」の名で追加しない。進捗・再開は既存のチェックリストと実行側の契約を使い、学習サービスに実行キューを新設しない。

## 10. 誤学習・失敗・削除

- **訂正と取消:** 項目id/versionを指定した管理操作による取消・忘却は、その確定時に即座に無効化する。自然文の訂正は現在の応答で優先するが、対応項目の特定と永続的な失効は次のバッチ分析で確定する。即時の永続反映が必要なら、通常応答で対象候補を示し管理操作へつなぐ。毎ターンの追加LLMや未実装の意味解析を前提にしない。同じ根拠からの自動復活を防ぐため、却下した出典/versionを保持する。単発の例外は項目全体の否定と区別する。
- **学習と承認:** 推測の保存、方針の採用、スキルの公開、実タスクの実行を別の決定にする。候補生成のたびに承認を要求しない。MVPで応答を変える候補は、根拠と範囲をまとめて提示して採用を受ける。後段の低影響な自動採用も、有効化時に対象範囲を明示する。
- **LLM失敗:** 有効項目を維持し、未処理差分を残す。指数backoffで最大3試行後、そのバッチを保留する。新バッチIDに変えて同じ失敗入力の再試行数・予算をリセットしない。再開は入力修正・設定変更・明示再試行に限る。
- **保存失敗:** 学習を停止して状態を表示する。既存会話確定を失敗へ書き換えず、学習側エラーを既存の`storeFailure`へ伝播させない。復旧時に保持イベントを再走査する。
- **再起動と並行:** 同じ共有workspaceのwriterは一つ。残ったpendingは対象hashとepochを検証して再開する。LLM呼出の外部重複まで完全には防げないため、再試行費用を計上し、結果commitはbatchIdで一度だけにする。複数Runner同時起動は既存worktree運用と同様に対象外。
- **チャットの削除/メッセージクリア:** 現行の共有記憶保持の意味を変えない。削除されたチャット限定項目は無効化し、分析中結果がそのscopeを再作成できないようepoch/存在を検証する。共有へ明示採用済みの項目は保持する。メッセージクリアだけでは学習を忘却しないことを表示する。
- **忘却:** 学習項目または全学習の明示削除を別操作として定義する。epochを進め、pending、候補、有効項目、根拠抜粋、関連評価とユーザー訂正、変更/利用履歴、生成スキル、保持版、取得cacheを対象範囲に応じて除く。既存ログに残る出典は再学習対象から除外する。全学習削除はその時点の高水位以前を除外し、項目削除は対応出典を除外する。

既存`clearMemory`は保持rawから再要約できるため、忘却APIの代用にしない。学習の忘却と会話原本・既存topicsの消去も同義ではない。ユーザーが情報そのものの削除を求める場合は、原本と既存記憶を含む削除範囲を明示し、既存削除経路との整合を別途設計する。旧学習版の復元で明示削除が復活しないことを必須条件とする。

## 11. 段階導入と評価

### 希望への適合度とユーザーによる訂正

学習・評価用モデルは同じ差分分析呼出で、変化があった対象とその会話について、ユーザーの明示した目標・希望への適合度を0〜100の暫定値として返す。評価レコードにはevaluationId、対象目標とversion、orchestrator/scope、対象期間・出典pair、実行モデル/settingsRevision、点数、根拠、理由、未確認事項を持たせる。採点基準は「0:希望と明確に不一致、50:一部適合し未解決あり、100:観測できた希望を満たす」とし、根拠不足は未評価（score=null）にする。無反応・次の話題への移行を満足と扱わず、全人格の満足度や客観的品質の保証として表示しない。

UIには「AIによる暫定評価」、対象と期間、点数または未評価、短い理由を表示する。ユーザーは「評価を変更」から編集し、「保存」で確定する。点数（0〜100）を指定すれば理由は任意で、点数なしなら空でない理由が必要。未変更・空入力は保存せず、同一の最新訂正は重複追加しない。元のAI評価は書き換えず、訂正id・対象evaluationId/version・ユーザー点数・任意理由・日時を別レコードにする。再訂正は履歴を残し最新の有効訂正を優先する。未反映訂正は同一評価内で個別・一括取消できる。旧形式の点数なし・理由空の訂正は反映済みでもresolution.itemIdが明示的にnullなら取消できる。取消日時を履歴に残し、元のAI評価・resolutionを書き換えない。有意味な反映済み訂正や学習成果を持つ訂正の取消は拒否する。取消済みと旧形式の空訂正は学習入力から除き、参照中のバッチは失効させる。UIはAI評価とユーザー評価を分け、根拠・期間・履歴を必要時に開く。容量上限で安全に保存できなければ訂正の保存失敗を返し、未保存の訂正を受理済みと表示しない。次の学習バッチは未反映の訂正を優先入力とし、会話pairが増えなくても対象にする。起動間隔・予算制限は維持し、反映先の学習versionまたは変更しなかった理由を記録する。

学習は具体的な希望、出典、訂正理由、採否と点数を合わせて判断する。点数だけで指示・権限・適用範囲を作らず、低い点数だけなら改善候補を保留してよい。異なる目標・期間・評価モデルの点数を単純に平均して「成長率」としない。評価対象の抜粋だけを使い、評価のために毎回全履歴を再送しない。

### 段階1: 応答を変えない観測

確定境界、出典、バッチ、モデル設定、予算、利用量台帳、再開、欠損表示、候補生成まで実装する。学習内容は応答やスキルへ反映しない。同じ固定会話例に対する手動ラベルと候補を比較し、明示指示・一時的例外・引用・訂正の区別を評価する。

### 段階2: 採用済み方針と先回り提案

取得契約、親への反映・撤回、候補のまとめて採用/却下、回答への配送表示、適合度評価とユーザー訂正を導入する。まずチャット限定の低影響な方針から始める。学習なしの場合と比較し、有用性が改善することを確認して共有へ広げる。

### 段階3: スキルと一括提案

専用スキルの公開・更新・統合・廃止、一覧・理由/差分履歴・参照表示と、現在の対象を確認した一括提案を導入する。実行権限・チェックリストは既存経路を利用する。利用結果が十分に集まるまではスキルの自動公開を有効化しない。

### 受入条件

| 検査 | 合格条件 |
| --- | --- |
| 確定・再送 | 部分応答・失敗・中断から成功を学習しない。正常完了と復旧完了が同じ入力になり、再送で反復数が増えない。 |
| 品質 | 「毎回短く」と「今回は短く」を区別し、引用の指示を採用しない。矛盾が解消されるまで自動昇格しない。 |
| 範囲・優先 | チャット限定項目が他チャットへ漏れず、現在の依頼・手動設定・固定承認規則を学習が上書きしない。 |
| 応答への反映 | 新規親・継続親・共有更新・同revisionで取得項目変更・子作業ありの各経路で、適用revisionとdigestが検証できる。取消後に旧方針を再利用しない。 |
| 費用・負荷 | 100ターンの模擬入力でも毎ターン分析せず、予約込み予算・並行数を守る。予算停止中も既存会話は継続する。 |
| 障害・競合 | 完了と学習保存の間、LLM完了とcommitの間で停止しても重複反映しない。削除中の旧結果が復活しない。 |
| 容量・欠損 | 未処理上限・raw pruning・ログ欠損時に学習状態が有界で、欠損を隠さず、要約cursorを止めない。 |
| スキル | 未管理ファイルや手動編集を上書きしない。統合後も適用条件を保持し、廃止・取消が取得結果へ反映される。 |
| モデル設定 | 共有設定の所有者が一つで、変更中バッチ/追加検証/再試行は旧snapshot、次バッチは新設定を用いる。未対応effortを無断変更しない。 |
| 可視化・訂正 | 配送、当該ターンの読取、継続親の参照を区別する。無反応は未確認、評価不能はnull。ユーザー訂正が元AI評価と別保存され、次バッチで優先される。 |
| 利用量・料金 | cached/reasoningの内数を重複加算せず、欠測・失敗・再試行・再起動・遅着精算でも二重計上しない。異通貨/不明単価を誤合算せず、集約前後と忘却後の保存範囲が一致する。 |
| 一括提案 | 対象と条件が明示され、拒否した同一提案を連発しない。提案採用が無関係な操作の許可にならない。 |

回帰確認の対象は既存の[voice-context-service.test.mjs](../private_runner/tests/voice-context-service.test.mjs)、[voice-memory-store.test.mjs](../private_runner/tests/voice-memory-store.test.mjs)、[voice-orchestrator-service.test.mjs](../private_runner/tests/voice-orchestrator-service.test.mjs)。実装時には上記の異なる契約と故障境界を検証し、単に実装をなぞるテストは増やさない。

計測は、学習呼出数・入出力usage・処理遅延・欠損数・応答遅延、有効提案の採用/拒否、同じ訂正の再発率、誤適用と取消件数を基本とする。提案の採用だけを作業成功と数えない。会話本文や秘密をメトリクスへ送らず、集計はローカルを基本とする。

導入の判断は「候補が増えた」ではなく、固定評価例で重大な誤適用がなく、実利用で再指示が減り、応答遅延と費用が許容範囲に収まること。比較期間・必要標本数・許容値は段階1の実測後に決め、現時点で改善率を約束しない。

## 12. 実装前に確認する点

1. 既存モデル実行経路を重複せず利用でき、ツール禁止・出力上限・usage取得が実際のランタイムで強制されるか。
2. 継続親への学習context配送、revision管理、取消時の安全な親切替が既存の子作業・チェックリスト読込と両立するか。
3. イベント確定後の観測と復旧をどこに接続すれば、通知の失敗や学習障害で会話状態を壊さないか。出自付きイベント再走査が既存pruningと整合するか。
4. 学習・評価用モデルの固定評価結果と予算。実モデル、effort、usage内訳・累積値の取得範囲、契約別単価の入力元を確認する。取得不能は不明として扱い、実価格はこの設計変更で調査・固定しない。
5. 専用スキル読取ツールの公開版/範囲検証・更新反映・客観的読取記録、共有モデル設定と評価訂正のUI接続、忘却と利用量台帳の保持範囲を確認する。

最初の実装は段階1に限定し、その後の依頼で段階2・3へ進めた。合成会話、偽モデル、隔離したApp Server、少数の実APIで契約を確認する。実利用の長期品質と実機UIは別の確認対象である。対象条件がある項目は、当該ターンの成功したツール出力に対象名がある場合だけ専用`read_context`から取得し、返却した項目も親の失効判定へ含める。条件確認不能になった次ターンでは旧親を再利用しない。
