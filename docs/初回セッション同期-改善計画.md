# 初回セッション同期 改善計画

作成日: 2026-10-26
状態: 両段階の実装・自動テスト・実API検証済み。実機への反映と初回25ディレクトリの一覧完了時間の短縮を確認。UI表示終了と起動全体の効果は未確定。
前提: [Git Worktree手順](GIT-WORKTREE.md)、[通信量削減の既存計画](通信量削減-修正計画.md)

## 1 目的と最初の変更

起動時の「セッション同期中」で必要な最新情報を保ち、一覧補完で使わない大きな本文の転送を減らす。
最初の変更は、HTTP `/session-summaries` の `firstUserMessage` を不要な呼び出し元だけ省略できるようにする。
同期の完了条件や取得頻度は変えず、実測で効果を確認してから次の対象を決める。

## 2 確認済みの通信とコード

### 起動直後の観測

2026-10-26 13:13:21 JSTから最初の約60秒について、iOSアプリの既存 `network_usage_snapshot` は次の受信量を記録している。

| 経路 | 受信バイト数 |
| --- | ---: |
| アプリ全体 | 14,087,953 |
| HTTP合計 | 9,395,911 |
| HTTPのうち session-summaries | 4,730,171 |
| WebSocket合計 | 4,692,042 |

これらはアプリ全体の観測で、初回同期だけを分離した値ではない。本文中心の計測であり、実回線上の圧縮後通信量とも一致しない。
初回25ディレクトリの一覧完了は計測開始から8.96秒だった。26回目は約41.37秒後の既存ディレクトリ再取得であり、初回完了まで約41秒かかったとは扱わない。
子セッション取得は当初観測区間で14回・12ディレクトリだった。
複数ディレクトリへの正当な取得を含むため、この件数だけで重複ループとは判定しない。

### 大きな本文が使われない経路

- [`useLlmSessionExplorer.ts`](../expo/src/features/app/hooks/useLlmSessionExplorer.ts) の `fetchRunnerSessionSnapshotMap` は、一覧を `/session-summaries` で補完する。
- 同ファイルの `buildRunnerSessionSnapshot` はコンテキスト使用率・モデル・推論強度・ツール表示・既読時刻を利用し、`firstUserMessage` は利用しない。
- [`llm-session-service.mjs`](../private_runner/src/llm-session-service.mjs) の `getLlmSessionSummaries` は、対象セッションの `firstUserMessage` を応答に含める。
- [`useSkiaMiniChatSessions.ts`](../expo/src/features/app/hooks/useSkiaMiniChatSessions.ts) は同じAPIの `firstUserMessage` をカード名の候補に使うため、全呼び出しで削除すると表示が変わる。

現行APIの5行ずつの応答から `firstUserMessage` だけを除いた比較は次のとおり。

| サンプル | 現行応答 | 本文フィールド除外後 |
| --- | ---: | ---: |
| A | 90,651 B | 3,205 B |
| B | 43,244 B | 2,626 B |
| C | 187,660 B | 3,251 B |

この比較には子セッションの行も含まれ、実装後の初回起動そのものを測った値ではない。
サンプルでは転送本文を大幅に減らせるが、起動全体の削減率・待ち時間は変更後に測定する。

## 3 変更するAPIと責任範囲

`POST /session-summaries` のリクエストに、任意の `includeFirstUserMessage` を追加する。

| 指定 | 応答 |
| --- | --- |
| 未指定 | 現行どおり `firstUserMessage` を含む |
| `true` | 現行どおり `firstUserMessage` を含む |
| `false` | 各行から `firstUserMessage` だけを省く |

省略は真偽値の `false` だけで有効にし、空文字や文字列 `"false"` などを暗黙変換しない。省略時はJSONのキー自体を送らない。
省略の判断は `getLlmSessionSummaries` の応答組み立てに置き、Codexとそれ以外のbackendで同じ契約にする。
`firstUserMessage` 以外のフィールド・値・欠損表現、ディレクトリ範囲、行の順序、`missingSessionIds` を維持する。
省略しない呼び出し元の応答形式は変えない。

[`runnerSessionSummaries.ts`](../expo/src/features/app/utils/runnerSessionSummaries.ts) は任意指定を各100件バッチのリクエストに渡す。
Explorerの `fetchRunnerSessionSnapshotMap` だけが `false` を指定する。Skiaの呼び出しは未指定のままにする。
クライアントの既存正規化では省略された本文を空文字として扱え、Explorerが必要とするメタデータはそのまま利用できる。

APIサービスに限定した1つの指定で、必要のない本文がネットワークへ出ることを止める。
画面側で受信後にフィールドを捨てる処理や、任意フィールドを選ぶ汎用フレームワークは追加しない。

## 4 最新情報を維持する条件

毎回のAPI呼び出しで従来と同じ取得処理を実行し、その時点の値を返す。
キャッシュ期限・再取得の間引き・古い応答へのフォールバックは追加しない。
`updatedAt`、`lastReadAt`、`contextUsage`、`modelRef`、`reasoningEffort`、親子関係などは省略対象にしない。
初回取得・通常更新・子セッション取得の対象範囲や、一覧のページ継続も変更しない。

## 5 第1段階で変更しない範囲

- WebSocketのプロトコル、一覧取得の並列数、ディレクトリの取得順序、同期中のUI。
- 音声の軽量化、ほかのAPIへのキャッシュ展開、既存の `/client-state` ETag対応。
- 本文ファイルの読み取り省略やreaderの分割。まず応答の転送量だけを減らす。

一覧の取得回数が必要かどうかは、本文削減後のログで判断する。
今回の変更に、未確認の重複取得抑止や別のリファクタリングを混ぜない。

## 6 テストと合格条件

### サービスとHTTP API

- 未指定・明示 `true` の応答が従来どおりで、真偽値の `false` だけが本文キーを省く。文字列などでは省かない。
- 同じフィクスチャへの両形式の応答を比較し、`firstUserMessage` を除く全フィールドが深く一致する。
- Codex・非Codex、空配列・存在しないID・入力順序・重複ID・ディレクトリ範囲を確認する。
- 隔離したフィクスチャでメタデータ更新と既読変更を行い、続く取得が両形式とも最新値を返す。
- 認証、JSON不正、32 KiB本文制限、1リクエスト100件上限と101件拒否を確認する。

### クライアント

- `runnerSessionSummaries.test.ts` で未指定時の互換性、各バッチへの `false` の伝達、101件の100件＋1件分割を確認する。
- `useLlmSessionExplorer.test.ts` でExplorerの指定と、取得後のモデル・使用率・既読等の保持を確認する。
- `useSkiaMiniChatSessions.test.tsx` で本文を含む既定リクエストとカード名の表示を維持する。
- バッチ失敗・タイムアウト時の既存エラー処理を維持する。

関連するNodeサービス・APIテスト、Jest、iOS/macOSの型チェック、`git diff --check` を実行する。
別担当のレビューで、省略対象の限定・最新値の維持・不要な抽象化がないことを確認する。
長い初回プロンプトを持つフィクスチャで応答バイト数の減少を確認し、表示に必要な情報が欠けないことを合格条件とする。

## 7 再起動後の実API確認

専用worktreeは `perf/session-startup-summary-payload`、基点は `/client-state` 対応済みの `83333ea` とする。
依存関係とローカル設定の準備後、対象worktreeの再起動・必要なアプリビルドのコマンドを提示する。
サーバー再起動と実機ビルドはユーザーが実行し、その連絡後にエージェントが確認する。

1. 稼働プロセスの作業ディレクトリが対象worktreeであることを確認する。
2. 既存の `/client-state` ETagの200・304が維持されていることを読み取りだけで確認する。
3. 同じディレクトリ・backend・ID集合に対し、本文あり／なしを交互に取得し、件数・順序・他の全メタデータを比較する。
4. 複数回の応答バイト数と所要時間を記録する。測定間に状態が更新された場合は一致比較と速度比較を分ける。
5. 同条件のアプリ起動で「セッション同期中」の時間と経路別受信量を測り、Skiaのカード名と最新状態の表示を確認する。

実データを更新する確認は行わず、変更後の鮮度は隔離フィクスチャのAPIテストで検証する。
公開Cloudflare経路が403などでAPIへ到達しない場合は、その経路の未確認を明記し、認証設定を変更しない。
コミット・push・PR・マージは既定のworktree手順に従い、外部送信とマージには必要な明示承認を得る。

## 8 第1段階の効果確認後の判断

初回同期が引き続き重い場合は、残った転送量と待ち時間を測って次の対象を選ぶ。
候補は、既存agent一覧の `contextUsage` を `agent-runtime.mjs` と `threads.ts` で保持し、補完HTTP取得自体を減らすこと。
これを第2段階として調査し、従来HTTPとモデル・既読時刻が同じになる第11節の方式を採用した。

## 9 第1段階の実装と自動テストの結果

本番変更は `llm-session-service.mjs`、`runnerSessionSummaries.ts`、`useLlmSessionExplorer.ts` の3ファイルに限定した。
サービスの既存serializerに指定を渡し、Explorerだけが省略を要求する。reader・取得頻度・キャッシュは変更していない。

- Nodeのサービス・summary API・既読API・履歴差分API・client-state APIテスト: 55件成功。
- Jestのsummary helper・Explorer・Skiaテスト: 3スイート83件成功。旧サーバーが指定を無視する互換性も確認した。
- iOS/macOS型チェック、Node構文確認、`git diff --check`: 成功。
- 隔離した長文プロンプトの実HTTPフィクスチャ: 193,231 Bから1,187 Bへ減少し、本文キー以外は深く一致した。
- 同じフィクスチャを更新し、再取得で最新のモデル・推論強度・コンテキスト使用量・既読時刻が返ることを確認した。

このフィクスチャの削減率をアプリ初回起動全体の効果とは扱わない。

## 10 第1段階の再起動後の実APIと起動ログ

ユーザーによる再ビルド・再起動後、稼働サーバーの作業ディレクトリが対象worktreeであることを確認した。
読み取りだけの実API検証で、既存client-stateの200・本文0 Bの304を確認した。同一ID集合の本文あり／なしを各3回比較し、本文キー以外の全フィールドが深く一致した。

| 対象 | 本文あり | 本文なし | 所要時間の中央値 |
| --- | ---: | ---: | --- |
| 1行 | 765 B | 743 B | 8.04 → 7.66 ms |
| 5行 | 43,244 B | 2,626 B | 6.42 → 6.32 ms |
| 5行 | 187,660 B | 3,251 B | 29.56 → 27.35 ms |

所要時間はloopback HTTPの値で、モバイル回線やアプリ起動の待ち時間を表さない。
iOS起動ログの初回25ディレクトリ完了は、変更前の13:13:21開始が8.96秒、14:34:16開始が8.65秒、変更後の14:37:37開始が9.21秒、14:39:59開始が9.08秒だった。
summary受信量は変更前の最初の約60秒で4,730,171 Bと4,672,967 B、変更後は25.84秒間で874,097 Bと57.46秒間で831,172 Bを観測した。
同じ操作・ID集合・観測時間を固定した比較ではないが、summary通信は約4.7 MBから0.8〜0.9 MBへ減った。一覧完了時間は約9秒のままで、体感の待ち時間が短くなったとは判断できない。
同期完了・描画完了の専用イベントはなく、この秒数は計測開始から初回25ディレクトリの一覧が完了するまでの代理指標である。変更後の別HTTP通信は約58秒間で約20 MBに達する観測もあり、起動全体の通信削減や高速化は確定していない。

第1段階は一覧→summary補完とメタデータ読み取りの順序を維持しており、待ち時間の区間と同じsummaryの二重読取を次の対象とした。

## 11 第2段階 一覧で取得済みのsummaryを再利用する

CLI rolloutで読んだ `contextUsage` は一覧の変換で欠落していた。一覧モデルはbindingの選択を優先するため、HTTPのnativeモデルとは値が異なり得る。Explorerは同じIDのHTTP summaryを再取得していた。
読み取り比較でも、一覧の20〜38 msに加えてHTTP補完に8〜27 msかかる例を確認した。これは起動全体の内訳を確定する計測ではない。

一覧のCLI読取が成功した項目だけに、任意の `summary` を同梱する。4フィールドは `contextUsage`、`modelRef`、`reasoningEffort`、`lastReadAt` で、本文は含めない。
`modelRef` と推論強度はnative summaryの値を保ち、binding優先の一覧モデルと分離する。`lastReadAt` は既に取得済みの同ID ACPの値と比較し、HTTPと同じ新しい方を使う。
同じIDのCLI rolloutが複数ある場合は同梱せず、従来のHTTPが選ぶファイルを維持する。旧サーバー・raw・ACP・非Codex・読取失敗もHTTP補完を続ける。

Explorerは同梱summaryを既存のsnapshot変換で使い、足りないIDだけをHTTPへ送る。明示的な `contextUsage: null` は情報欠損と区別する。
HTTP補完や認証解決が失敗しても同梱済み情報を残す。`includeRunnerSnapshots: false`、ページ継続、親子範囲、取得頻度は従来どおりで、TTLや新しいキャッシュは追加しない。
既存の `session_history_fetch_done` と `session_child_history_fetch_done` に、`listElapsedMs`、`runnerSnapshotElapsedMs`、`runnerSnapshotRequestedCount` を加え、一覧待ちと補完待ちを分けて測る。

- Node関連7ファイル118件、Jest関連4スイート109件、iOS/macOS型チェック、Node構文確認、差分チェックが成功した。
- 隔離した実APIで一覧の4フィールドとHTTPが深く一致し、読取失敗後の再取得・同ID ACP既読・重複CLI・null使用量・nativeと選択モデルの違いを確認した。
- ExplorerのHTTP省略、混在backend、旧形式への補完、認証/HTTP失敗時の情報保持、子一覧、明示的な補完無効を検証した。

ユーザー再起動後、対象worktreeのサーバーが稼働していることを確認した。読み取りだけの実API比較で、3組・計11件のCLI行の同梱4フィールドがHTTP summaryと全件深く一致し、本文の重複もなかった。
実アプリのTS取得helperを実サーバーへ実行し、client-stateの200・458,402 Bから304・0 Bへの更新確認、古いETagでの最新200、不正tokenでの401、その後の正規取得304が成功した。
helloやモデルカタログ照会は次の計測候補だが、helloはv2互換判定を担い、一覧には版番号がないため単純削除しない。今回は変更しない。

## 12 第2段階の実機反映後の観測

実機再ビルド後のiOSログで新しい3指標を確認した。各計測開始時刻から最初の異なる25ディレクトリの一覧が完了するまでを比較し、後続の手動同期を除外した。

| 2026-10-26の計測開始時刻 JST | 初回25ディレクトリ完了まで |
| --- | ---: |
| 16:28:11 | 6.724秒 |
| 16:28:38 | 7.306秒 |
| 16:28:49 | 6.428秒 |
| 16:35:20 | 6.923秒 |
| 16:35:54 | 6.329秒 |

中央値は6.724秒で、従来の8.65・9.209・9.082秒に対して、およそ2〜3秒短い一覧完了区間を観測した。UIの同期表示終了を示す専用イベントはないため、これは起動全体や描画完了の時間ではない。
各初回の一覧行数・snapshot行数はともに97件を維持した。空一覧を除く23要求のうち21要求はHTTP補完が不要となり、残る2要求で補完したのは計4 IDだった。子一覧のHTTP補完も0件だった。
約60秒のsummary受信量は349,745 B・349,737 Bで、従来の約58秒の831,172 Bより少なかった。操作・観測時間を固定した比較ではないため、起動全体の通信削減率とは扱わない。
今回の起動ログではsummaryの新たな失敗・timeoutは確認されなかった。Git処理・存在しないセッションに関する既存エラーは残っており、今回の変更範囲には含めていない。
