## 2. ⑤で入った機能(以後の検証の道具)

- 計測ストア: `expo/src/features/ws/networkUsageMetrics.ts`(シングルトン)。3経路(http / runner-ws / stream-tts)別+HTTPカテゴリ別(session-messages / session-summaries / tts-media / その他)の送受信バイト累計。ホットパスでは加算のみ、UIは表示中のみ1秒ポーリング
- 計測点: `cloudflareAccessFetch.ts`(fetchパッチ、FormDataは下限推定)/ `RunnerWebSocketManager.ts`(送受信)/ `useSynthesizeSpeechStreamController.ts`(stream-tts WS。音声本体はexpo-avネイティブDLのため `audio_chunk` の `audioBytes` メタで推定計上、seq dedupe済み)
- UI: 接続ステータスバッジのタップモーダルに内訳+「通信量をリセット」。TTS波形カードのタップでTTS通信量詳細
- ログ: `/session-messages` 応答の `x-session-messages-response-bytes` / `content-length` / bodyバイトを既存 `session_diag` イベント(`runner_session_messages_done` 等)に追加 → client_auto_logs で後日集計可能
- 既知の制限: 表示値はbody実測の下限(TLS・プロトコルオーバーヘッド・multipart境界は含まず)。manager非経由のcodex直結WSフォールバックは計測対象外(標準構成では未使用)

### 修正効果の数値確認手順

1. アプリ内: バッジモーダルで「リセット」→ 同一シナリオを数分操作 → 経路別バイトを記録。各修正の前後で比較(⑤マージ時点のビルドがベースライン)
2. サーバー側: `private_runner/logs/client_auto_logs/*.jsonl` の `runner_session_messages_done` から `responseBytesHeader` を集計。relay生成数・close 1006件数は `logs/codex_ws_proxy/*.jsonl` で比較(修正計画書§2の集計方法参照)

## 3. 未解決の症状: LLM応答完了時にチャット画面がガクつく

実機確認で報告された症状。**⑤の変更が原因ではない**(計測は加算のみ、UI再描画はモーダル表示中のみ)。

- 所見: 完了ハンドラ(`expo/src/features/app/AppRoot.tsx:3763-3764` 付近)が完了のたびに `refreshDirectorySessionsAfterCompletion(directory)` と `refreshGitChangedFiles(force: true)` を呼ぶ。一覧refreshで `updatedAt` が変わるとhydrate署名が変化し(修正計画書§3.5、`MiniBoardScreen.tsx:207-213`)、履歴全文再取得→チャット画面の再描画が発生する
- 対処: 修正②(レート制御)・③(hydrate coalesce)・④(差分取得)で解消される見込み。②③の実装時にこの症状の再現確認をすること
- 裏取り方法: チャット送信直前にバッジモーダルでリセット→完了の瞬間に session-messages 受信バイトが履歴全文サイズ分増えるかを確認
