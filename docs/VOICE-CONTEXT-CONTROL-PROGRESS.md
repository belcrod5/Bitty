## 契約と境界

- 正本: [設計書](VOICE-CONTEXT-CONTROL-DESIGN.md) と [App Server 検証書](APP-SERVER-CONTEXT-VERIFICATION.md)。矛盾・未確定事項は記録して親に返す。
- 既存チャットは現行の native session のまま。音声会話だけ認証済み Runner WS 入口で一度分岐する。Agent Service と通常の Codex turn 処理へ方式判定を広げない。
- 音声会話は Runner の正本ログと `MEMORY.md` から文脈を選び、応答ごとに新規 ephemeral thread を作る。未要約の完了ペアは要約確定まで全件投入し、20メッセージ超を非同期で要約する。可視入力800,000 UTF-8 bytes超は黙って削らず明示失敗。要約範囲と生履歴を重複させない。
- 受理を同期保存してから確認し、同一送信IDの再送は再生成しない。再起動後の不明な native 実行は `unknown` で止める。
- 音声応答は Codex の MCP／apps 設定を継承し、承認要求を通常チャットの UI に渡す。要約だけはツール無効・承認なしとする。tool／reasoning item と承認状態のターン間継続は対象外。実モデルによるツール実行・承認は未検証。

### 2026-09-25 決定・前案の更新（未実装）

- 上の要約待ち中の文脈欠落案と32 KiB維持・32 KiB使用率表示案を撤回する。20履歴メッセージを超えた分は応答と独立して非同期要約するが、`MEMORY.md` への成功・永続確定までは未要約の完了メッセージを全件、確定済みの旧要約とともにモデルへ渡す。50メッセージ以上に増えても同様とし、要約済み範囲と重複させない。入力から外すのは要約確定後だけで、正本 `events.jsonl` は削除しない。
- 新しいユーザー発話では前の予約中・実行中の要約要求を中止して再計画し、古い結果が後から返っても `MEMORY.md` に書けないようにする。応答は要約を待たずに進める。
- 現行32 KiBは固定指示・要約・選択ペア・今回発話の UTF-8 バイト数に対するアプリ独自の上限で、モデルの実際の context window ではない。現行実装はこの上限または5ペア超過時に古いペアを入力候補から外して同期要約する。新方針では未要約の50メッセージ等をこの上限で黙って落とさず、代替の容量境界とモデル上限付近の扱いを設計する。
- 月間 STT 時間の右に表示する候補は、32 KiB予算率から、自己計算による実モデル文脈使用率の推定値、未要約メッセージ件数、`MEMORY.md` 本文の Unicode 文字数へ変更する。3項目は共通の `StreamingSttFooter` 内に置き、`VoiceConversationScreen` で同コンポーネントが表示される間、既存の表示条件に従って見せる。録音中だけの新たな条件や別の表示領域は設けない。算出は音声側で行い、`VoiceConversationScreen` だけが任意 prop で渡す。`ChatScreen` は渡さず、既存表示を変えない。フッターに算出処理は置かない。文字数から機械可読ヘッダーを除き、表示上の文字の数え方は実装時に確定する。使用率の算出方法と表示名も設計時に確定し、実測の model context window 使用率と混同させない。
- 今後の検証: 要約の遅延・失敗・中止・結果到着順の逆転で欠落／重複／順序乱れがないこと、20件から50件超への連続発話、再起動、モデル上限付近、画面の未要約件数、既存チャット回帰を確認する。今回の更新は文書のみで、コード変更・テスト実行はない。
