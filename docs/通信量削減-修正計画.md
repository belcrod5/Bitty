# 通信量削減 修正計画書

作成日: 2026-08-01
改訂: 2026-08-01 第3版(2回のレビュー指摘を反映)
状態: 実装未着手

## 1. 問題

モバイル通信量が約3時間で2GB(平均190KB/s相当)発生した。

## 2. 実測で確認した事実

対象ログ: `private_runner/logs/codex_ws_proxy/20260801_114316_502.jsonl`、`private_runner/logs/client_auto_logs/20260801_114316_502.jsonl`(2026-08-01 11:43〜13:40 JST、約2時間)

- upstream WS(サーバー→codex app-server :4500、**localhost接続**)の新規openが169回。relayIdは全て異なる
- うち118回が11:50〜11:52(JST)に集中(1秒に2〜4回)。physical WS再接続(`upgrade_request`)直後にバースト
- closeは全135回とも code 1006。うち63本は**detachのちょうど30分後**に2バッチ(32本が5ms以内+31本が2ms以内)で一括発生。残り72本は生成時のeviction/churnと推定(eviction・TTL cleanupはログイベントを出さないため内訳は推定)
- RPC内訳: `initialize` 340 / `thread/read` 194 / `thread/list` 144 に対し、turn実行系は2回のみ。通信のほぼ全てが「一覧取得と履歴読み出しの反復」
- クライアント側: `session_history_fetch` 172回、`runner_session_history_restore` start 162回(done 158回)。同一セッションの再取得は最大61回(restore_start基準、sessionId別集計)。`panel_runtime_snapshot_cleared` 297回
- 現行ログに通信バイト数の集計はない。ただしサーバーは `/session-messages` 応答に `x-session-messages-response-bytes` ヘッダを既に付与している(`server-runtime.mjs:8884-8888`)→ クライアントでログするだけで最重量候補の実測が可能(修正項目⑤の第一歩)

## 3. 根本原因

### 3.1 モバイル2GBのバイト源(有力): 履歴・一覧の全文再取得の反復

リークしたupstream接続自体はlocalhostでありモバイル回線のバイトはほぼ消費しない。バイト源の有力候補は次の反復転送:

- `/session-messages` の全文取得 ×162回(キャッシュ判定なし: `AppRoot.tsx:6966-6972`、サーバーは `no-store`・ETag/304非対応: `server-runtime.mjs:8885`)
- `thread/list` ×144回+`/session-summaries` 再取得
- relay再アタッチ時の `replayAfterSeq: 0` による現ターン全再送(最大6000イベント、`server-runtime.mjs:9412, 11015-11048`)

これらを駆動するのが以下の構造問題(3.2〜3.4)。

### 3.2 原因A: threadIdなし単発RPCによるrelay蓄積(接続churnの源)

- クライアントの単発RPCは毎回固有のoperationIdを採番する(`expo/src/features/codex/client/rpcSession.ts:72-73`)
- threadIdを持つRPC(`thread/read` 等)はサーバー側のidentity index(`runner-ws-llm-relay-identity.mjs:62-94`)で既存relayを再利用し、initializeもキャッシュ応答される(`server-runtime.mjs:11688-11718`)
- 一方 **threadIdを持たないRPC(主に `thread/list`)は毎回新規relay+新規upstream WSを生成**する(`server-runtime.mjs:9390-9463, 11618`)。open 169回 ≒ thread/list 144回+初見thread分と整合
- 解放の実態: クライアントに解放opはなく(`rpcSession.ts:97` はmanager利用時素通り、サーバーのrelay channelはattach/resumeのみ: `server-runtime.mjs:9604`)、**physical WS接続中はrelayが蓄積し続ける**。切断後はdetach→runner自身の30分TTL(`CODEX_WS_RELAY_IDLE_TTL_MS`、`server-runtime.mjs:300-303`)でcleanupされる。上限64のeviction(`:11111-11119`)はclients付きrelayには効かない
- **「30分後の63本一括1006」の正体は、codex app-server側のidle切断ではなく、runner自身のTTLタイマーの一斉発火**(detach時刻+30分とミリ秒単位で一致)。1006になる理由(close frameの応答有無)は実装時に検証する

### 3.3 原因B: relay喪失通知→全文再hydrateの増幅

- physical WS再接続時、observerの `relay/resume` が `runner_relay_resume_miss` / `runner_relay_closed` 制御メッセージを受ける(`server-runtime.mjs:11559-11570, 9618-9628`)
- これを受けた回復処理(`useCodexRelayObserverStartController.ts:502-523` → `useSessionRelayLossRecoveryController.ts:110-172`)が、可視セッション+パネル表示分の**HTTP `/session-messages` 全文再hydrate**を並行発火する(バイト増幅の主経路)。なお回復経路自体はthread/listを呼ばず、新規relayも作らない(attach/resumeは既存relayの解決のみ: `server-runtime.mjs:9604-9641`)。thread/listによる新規relay生成は、並行して走る一覧refresh側(トリガーは③で特定)
- 抑制ガード `RELAY_LOSS_RESYNC_MIN_INTERVAL_MS=5000`(`AppRoot.tsx:567`)はセッション単位のため、複数パネル並行時は合算レートが超過

### 3.4 原因C: physical WS再接続時の再hydrate fan-out

- 再接続のたびに複数パネルが並行で `hydratePanelFromSessionHistory` を実行し、論理relay作成・履歴取得側にバックオフ・debounceがない。「1秒に2〜4回」は並行fan-out
- 注意: 駆動経路は未特定(候補: `MiniBoardScreen.tsx:207-213` のhydrate署名変化)。**修正③の先頭タスクとして駆動経路の特定を行う**

### 3.5 補助要因

- セッション本文のキャッシュ不在(上記3.1)に加え、ミニボード画面アンマウントで全12パネルのスナップショット一括クリア(`MiniBoardScreen.tsx:350-358`)、hydrate署名が `updatedAt` を含み一覧refreshのたび全再hydrate(`MiniBoardScreen.tsx:207-213`)
- TTS: 配信 `no-store`(`server-runtime.mjs:8927`)、リプレイは全文再合成+再ダウンロード(`useReplyAudioFlowController.ts:41-67`)。通常再生は最大約0.94MB/分で単独では2GBに届かない(主因ではない)

## 4. 修正項目(優先順)

### ⑤ 通信量の計測と可視化【先行実施を推奨】

先行理由: リーク(原因A)はlocalhostでモバイルバイトを消費しないため、「2GBのバイト源は再取得ループ」という3.1の推定を数値で確定させてから①〜④の効果を測るのが安全。

- 第一歩(即日可能): クライアントで `/session-messages` 応答の `x-session-messages-response-bytes` / `content-length` をログ集計
- 本実装: 次の**3関所**で全通信を経路別集計する
  - HTTP: `cloudflareAccessFetch.ts:56-77`(fetchモンキーパッチ)
  - runner-ws: `RunnerWebSocketManager.ts`(送信 `:403-411`/受信 `:536-540`、既存件数カウンタにバイト数を追加)
  - stream-tts WS: `useSynthesizeSpeechStreamController.ts` の受信ハンドラ(`/stream-tts` はRunnerWebSocketManagerを通らない独自WSのため個別にカウンタを追加。§3.5のTTS見積りの検証にも必要)
- UI: 接続ステータスバッジ(`RunnerWsConnectionStatus.tsx:114`、既存モーダル)に通信量内訳を追加。TTSリング(`TtsWaveformPlayer.tsx`)にタップ詳細を追加

### ① relay蓄積の解消(接続churnの根治)

- 方針: **threadIdなし単発RPC(実質 `thread/list`)を、physical WS接続ごとの共有relayにルーティング**する。これで新規relayの約85%が消える。全面的なupstream多重化は不要
- 設計制約: turn実行relayと単発RPC共有relayは**分離必須**。`forwardCodexRelayClientData` のidentity再bind(`server-runtime.mjs:11738-11741`)と通知フィルタ(`upstream_to_client_rpc_ignored_thread_mismatch`、ログ60件)への回帰に注意
- 段階投入できる即効ノブ(本体の前後に併用可):
  - `CODEX_WS_RELAY_IDLE_TTL_MS` の短縮(env変更のみ)
  - 単発RPC(identityあり・turn未開始・threadIdなし)の応答送信後にサーバー側でrelay自動close(ack送信とcloseのrace・同一opの追加RPCに備え、最終応答後に短いグレース期間を置いてclose)
  - evictionをattached-idleな単発RPC relayにも拡張
- 主な変更箇所: `server-runtime.mjs`(relayルーティング)、必要なら `rpcSession.ts`

### ② relay喪失回復のレート制御

- 制御対象は全文再hydrateの発火(`selectSpecificLlmSession` / `hydratePanelFromSessionHistory`)。現状のセッション単位ガードをグローバル合算のレート制御に変更する(閾値は⑤の計測を見て実装者が調整)
- 注: 回復経路が新規relayを作らないことは現状既に満たされている(3.3参照)ため、relay生成の抑止は②の対象外

### ③ 再接続時hydrateのcoalesce

- 先頭タスク: fan-outの駆動経路を特定する(3.4参照。現状は候補のみ)
- 再接続直後の全パネル再hydrateを、1回の `thread/list` +差分に集約(debounce。時間は実装者判断)
- 既存relayの `resume` を優先し新規作成を抑止

### ④ 差分取得+端末ファイルキャッシュ

- 前提調査: `/session-messages` は既に `limit`/`cursor` を持つ(`server-runtime.mjs:8853-8865`)。既存cursor pagingの意味論と差分取得への流用可否を先に確認する
- relay再アタッチ: `replayAfterSeq: 0` をやめ、実受信済みseqを渡して差分再開
- `/session-messages`: クライアントが保持済み最終位置(seqまたはcursor)を送り、サーバーはそれ以降のみ返す(履歴はappend-onlyで相性が良い。c36997cで不変性も担保済み)。旧クライアント互換のため未指定時は現行挙動
- 端末側: expo-file-systemにセッションごと追記保存する永続キャッシュ+メモリstoreの2層。容量上限・掃除ポリシー・seq不整合時の破棄(値は実装者判断、⑤で調整)
- ミニボードのスナップショット過剰クリア(`MiniBoardScreen.tsx:350-358`、署名の `updatedAt` 依存)も修正

### 対象外(今回はやらない)

- TTSの合成キャッシュ・リプレイ時再合成の廃止(主因ではない。⑤の計測後に別タスクで判断)
- STT・クライアントログ送信の削減(量的に軽微)

## 5. 実装の進め方

- GIT-WORKTREE.md のフローに従い、1項目=1ブランチ=1worktreeで実施
- 推奨順序: **⑤(計測)→ ①(relay根治)→ ②③(安全網)→ ④(差分+キャッシュ)**
- 各PRの検証: 修正前後で⑤の計測値(経路別バイト数)と `codex_ws_proxy` ログのrelay生成数・1006件数を比較

## 6. リスク・注意点

- ①はrelayルーティングの変更のため、turn実行中のイベント配送・複数デバイス同時接続・通知フィルタの回帰確認が必須(スコープを「threadIdなしRPCのみ」に絞ることでリスクを限定)
- ④のサーバーAPI変更は旧クライアント互換に注意(未指定時は現行挙動にフォールバック)
- 検証はworktree側スクリプトで行い、実機ビルド+サーバー再起動コマンドをユーザーに提示する(GIT-WORKTREE.md 3.2)
